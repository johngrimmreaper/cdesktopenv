# dtksh ksh93 upstream submodule

CDE builds `dtksh` using the upstream `ksh93/ksh` source tree checked out as a Git submodule at this path, relative to the `cde/` source directory:

    programs/dtksh/ksh93

The submodule is intentionally pinned to a specific upstream commit recorded by the CDE repository. It does not automatically follow an upstream branch.

Release tarballs generated by `make dist` include the ksh93 source as normal files, without Git metadata. Tarball users should not need to initialize Git submodules.

Future ksh updates should be reviewed as normal CDE changes by updating the pinned submodule commit, refreshing any CDE-side patches, and testing the build.

## Fresh clone

To clone CDE and fetch the ksh93 submodule in one step:

    git clone --recurse-submodules https://git.code.sf.net/p/cdesktopenv/code cdesktopenv

## Existing checkout

If CDE was already cloned without submodules, initialize and fetch the ksh93 submodule with:

    cd cdesktopenv
    git submodule update --init --recursive

If the submodule URL changes in the future, synchronize the local checkout first:

    cd cdesktopenv
    git submodule sync --recursive
    git submodule update --init --recursive

## Updating ksh93 in CDE

CDE should not treat the upstream ksh93 source as locally owned code.

A subtree makes ksh look like CDE-owned code; a submodule makes it clear that CDE is pinning a known upstream ksh release, with local CDE deltas kept as reviewable patches.

Recommended update policy:

1. choose a specific upstream ksh release tag or commit;
2. update the submodule to that exact commit;
3. keep CDE-specific changes as CDE-side patches;
4. build and test `dtksh`;
5. commit the updated submodule pointer and any refreshed CDE-side patches through normal review.

This keeps the upstream ksh history auditable while preserving CDE control over when ksh is updated.
